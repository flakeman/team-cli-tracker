# SDD-02 Near-Term Execution Plan

## Context
Базовая архитектура и деплой-контур уже определены в `SDD-01`. Нужен конкретный технический этап, который превращает каркас проекта в рабочий MVP для командной CLI-работы.

## Goal
Реализовать минимально рабочий децентрализованный трекер с подписанными событиями, P2P-синхронизацией, базовыми командами задач, CLI-доской и защищенной проверкой переходов через Raft-контур.

## Scope
1. Идентификация ноды и append подписанных событий.
2. P2P-discovery пиров и синхронизация состояния.
3. Базовые команды задач: `create`, `transition`, `comment`.
4. CLI-рендер доски из реплицированного состояния.
5. Проверка переходов через защищенный Raft-контур.

## Out Of Scope
- Полноценный UI (web/mobile).
- Полный CRDT-набор для всех типов полей.
- Интеграции с внешними трекерами (Jira/YouTrack) в рамках этого этапа.

## Functional Requirements
1. Node identity:
- каждая нода имеет устойчивый `node_id`, keypair и подпись исходящих событий.
- события отклоняются при невалидной подписи или несоответствии signer/node.

2. Signed event append:
- события записываются в append-only журнал.
- каждая запись содержит `project_id`, `entity_id`, `event_type`, `seq`, `signer_id`, `signature`, `timestamp`.
- повторная запись с тем же `(project_id, signer_id, seq)` отклоняется (replay protection).

3. P2P discovery and sync:
- нода обнаруживает пиров из конфига и/или через discovery слой.
- поддерживается запрос отсутствующих диапазонов событий по vector clock.
- после восстановления соединения нода догоняет актуальное состояние.

4. Issue commands:
- `issue create`: создает карточку через событие.
- `issue transition`: меняет статус через событие и policy-check.
- `issue comment`: добавляет комментарий через событие.

5. CLI board render:
- CLI строит канбан-доску из локально реплицированного состояния.
- вывод поддерживает plain и JSON режимы.
- отображаются колонки, счетчики, карточки и базовые атрибуты.

6. Raft-protected transitions:
- проверка допустимости перехода выполняется через защищенный Raft-контур.
- при недоступности кворума переход блокируется с понятной ошибкой.
- в admin-preferred режиме приоритет лидера у admin-ноды, но failover сохраняется.

## Non-Functional Requirements
- p95 локального чтения доски < 100ms.
- p95 применения локального события < 200ms (без учета сети).
- сходимость состояния после reconnect в малой команде <= 10s.
- аудит-цепочка должна верифицироваться на каждой ноде.

## Acceptance
1. Нода стартует с валидной идентификацией и подписывает события.
2. События отбрасываются при невалидной подписи или replay.
3. Две и более ноды после reconnect приходят к одинаковому состоянию задач.
4. Команды `create/transition/comment` доступны из CLI и отражаются на доске.
5. Запрещенный переход отклоняется Raft-policy слоем.
6. При падении preferred admin leader кластер продолжает работу через re-election.
